# connector-connector-mcp ("cc")
Connector Connector: add, remove, update, list and verify MCP connectors on claude.ai, ChatGPT and Grok. Rules for anyone working here: `CLAUDE.md`. Design: `docs/SPEC.md`.

## How the browser side works, in one paragraph
Every cc run drives its own Chrome process on its own copy of a signed-in "master" profile, so any number of callers (CLI, MCP server, several Claude threads) can run at the same time without touching each other's tabs.
The master profile is signed in ONCE by copying the sign-ins out of a Chrome you already use; after that it keeps itself fresh. Steps 3 to 6 below are the only setup this model adds.

## Full walkthrough, step 1 to done
Every step is tagged **[SCRIPTED]** (run the command, nothing to decide) or **[MANUAL]** (a person does it in an app, listed click by click). Run all commands from the cc repo folder in PowerShell on the HELM host.

1. **[SCRIPTED]** Install dependencies and build.
   `npm ci` then `npm run build`. Produces `dist\`. Nothing to copy.
2. **[SCRIPTED]** Create the tunnel, DNS record and secrets file for each environment (skip if already done; it never overwrites an existing secrets file).
   `.\scripts\setup-host.ps1 -Environment production` then `.\scripts\setup-host.ps1 -Environment test`.
   Produces `%LOCALAPPDATA%\HELM\connector-connector-mcp\<env>\secrets\connector.env` (contains `CC_MCP_BEARER_TOKEN`; never printed). The token goes to whoever registers the cc connector itself: cc reads it by reference from that file.
3. **[MANUAL]** Make sure ONE Chrome on this machine is signed in to all three sites. Use the Chrome that is already running with remote debugging on port 9222 (the shared HELM browser). If none is running, start one: Windows key, type `cmd`, Enter, then
   `"C:\Program Files\Google\Chrome\Application\chrome.exe" --remote-debugging-port=9222 --user-data-dir=%TEMP%\cc-signin` and press Enter. In that Chrome window:
   1. Address bar: type `claude.ai`, Enter. If you see a login page, click **Continue with Google**, click the account `trenterrolthomas@gmail.com`, click **Continue**. Wait until your chats list is visible.
   2. Address bar: type `chatgpt.com`, Enter. If you see **Log in**, click it, click **Continue with Google**, click the same Google account. ChatGPT then texts a code to your phone: type it into the **Code** box and click **Continue**. Wait until the chat page is visible.
   3. Address bar: type `grok.com`, Enter. If you see **Sign in**, click it, click **Login with email**, type the email, click **Next**, type the password, click **Log in**. (The Grok email and password are in the vault under the label `Grok`.) Wait until the chat page is visible.
   Produces: nothing to copy. The sign-ins now live in that Chrome, which step 4 reads.
4. **[SCRIPTED]** Copy those sign-ins into cc's cold master profile.
   `node bin\cc.mjs browser seed --from-port 9222`
   Expected output, one line per platform: `claude     N cookies copied, signed in: yes` (and the same for `chatgpt` and `grok`). Produces the folder `%LOCALAPPDATA%\HELM\connector-connector-mcp\browser-master` (override with `CC_BROWSER_MASTER`). No cookie value is printed or written anywhere else. Leave the source Chrome running or close it; cc does not use it again.
5. **[SCRIPTED]** Prove the master works in a throwaway browser.
   `node bin\cc.mjs browser check`
   Expected: `claude signed in: yes`, `chatgpt signed in: yes`, `grok signed in: yes`, exit code 0. The browser it launched is closed and deleted when the command ends.
6. **[MANUAL]** Only if step 4 or 5 printed `NO` for a platform: repeat the matching sub-step of step 3 in the source Chrome (that platform's login is missing or expired there), then run step 4 again. Nothing else changes.
7. **[SCRIPTED]** Deploy and start (stop the running instance first; the deploy refuses a running one).
   `node scripts\deploy.mjs production <tag>` (a release tag such as `v0.2.12`, never a branch) then `node scripts\install-tasks.ps1 -Environment production -Start`; repeat with `test`.
   Produces `deploy\<env>\DEPLOYED.json` (commit that is running) and the four AtLogOn scheduled tasks.
8. **[SCRIPTED]** Prove concurrency on the real platforms: three runs at the same moment, three separate browsers.
   `Start-Process node -ArgumentList 'bin\cc.mjs','verify','helm-drive','--platform','claude' -RedirectStandardOutput $env:TEMP\cc-a.log; Start-Process node -ArgumentList 'bin\cc.mjs','verify','helm-shell','--platform','chatgpt' -RedirectStandardOutput $env:TEMP\cc-b.log; Start-Process node -ArgumentList 'bin\cc.mjs','verify','vault-mcp','--platform','grok' -RedirectStandardOutput $env:TEMP\cc-c.log`
   Wait about a minute, then `Get-Content $env:TEMP\cc-a.log,$env:TEMP\cc-b.log,$env:TEMP\cc-c.log`. Expected: three `ok verify ...` lines and no `Target page, context or browser has been closed`.
9. **[SCRIPTED]** Routine use (nothing to set up): `node bin\cc.mjs add <id> --platform all`, `verify`, `remove`, `list`, or the same through the `cc_run` MCP tool. One call covering several platforms gives each platform its own browser and lets them overlap as far as the machine has spare CPU and memory (a polite admission gate: on a busy or weak machine they effectively run one after another, on a strong idle one they overlap; `CC_PLATFORM_PARALLELISM=1` forces one at a time, `CC_ADMIT_MAX_CPU` and `CC_ADMIT_MIN_FREE_GB` tune the gate, see `docs/SPEC.md` section 9). Concurrent callers are fine too; at most `CC_MAX_CONCURRENCY` (default 4) browsers run at once and extra callers wait, then fail with a clear "all lanes are busy" error after `CC_LANE_WAIT_MS` (default 120 s).

### Keeping the master fresh
Each healthy browser merges the sign-in cookies it rotated back into the master automatically (only if every platform it touched still showed a signed-in cookie; unchanged cookies are never written, so an older copy cannot overwrite a newer one). If a platform signs out anyway (password change, long idle), `cc browser check` says `NO`: do step 3 for that platform and step 4 again.

## More than one account (`--account`)
cc can work in several claude.ai accounts side by side. Each account is listed in `registry/accounts.json` (id, email, which platforms it is used on, the name of its vault entry) and gets its **own** master browser profile, so a run for one account never sees or changes another account's connectors. The account without a `master` folder name is the original one and uses the default master; every other account's master sits next to it (for `trentfromrid`: `%LOCALAPPDATA%\HELM\connector-connector-mcp\browser-master-trentfromrid`). Every op takes `--account <id>` (MCP: `account` on `cc_run`); without it cc uses `CC_ACCOUNT`, else the file's `default`. A platform the account is not used on is reported `skipped`. `node bin\cc.mjs accounts` lists them.

Signing an account in is automatic: `cc browser signin --account <id>` opens a browser on that account's own master, goes to claude.ai, clicks **Continue with Google**, types the account's email and password from its vault entry, clicks Google's **Continue** to claude.ai, and checks with claude.ai that the signed-in email is the account's own (a different email is removed again and reported). It never ticks a box or clicks Allow, and never picks another account's tile in Google's account chooser (operator decision 2026-10-19; CLAUDE.md rule 8). The password is resolved inside the process from `bw serve` and never printed or logged.

## Google OAuth renewal (`cc reauth`)
Connectors that talk to Google (the Drive and Audio connectors) hold a refresh token that Google expires after 7 days while the OAuth app is in Testing status. cc renews them; connector repos carry no renewal script. Design and safety properties: `docs/SPEC.md` section 10.
1. **[SCRIPTED]** Declare it in the connector's registry entry (`registry/connectors.json`): `googleOAuth: { secretsDir, scopes, account: { vaultLabel }, host?, restart?, health? }`. `host` (`ssh`, `keyFile`, `os`, optional `transport`) is only for a connector whose server runs on another machine (`transport: "gate"`, below, is for a NAS login that allows only `put` and `health`); `restart` and `health` run on the connector's own host. Only references and paths, never a secret value.
2. **[SCRIPTED]** Check every prerequisite without opening a browser or changing anything: `node bin\cc.mjs reauth --all --dry-run` (add `--include-test` for test-tier connectors). Expected per connector: `credentials.json readable ...; vault entry "..." found (username present, password present); token.json present; ... restart configured; health configured`.
3. **[SCRIPTED]** Renew now: `node bin\cc.mjs reauth helm-audio-mcp` (ids, or `--all` for every production connector with a `googleOAuth` block). cc opens one browser on its master profile, walks Google's consent for the declared scopes, delivers the new `token.json`, restarts the connector and checks its health; if the health check fails it puts the old token back. Output never contains a code, token or password. Logs: `%LOCALAPPDATA%\HELM\connector-connector-mcp\logs\reauth.log`.
4. **[SCRIPTED]** Schedule it (deploy first, then): `.\scripts\install-reauth-task.ps1 -Environment production -Start`. Registers "cc-mcp Google Reauth" (every 5 days at 03:30; `-At` changes the time), switches on Task Scheduler history, and retires the legacy "HELM TT-MCP Google Reauth" task. Runner log: `%LOCALAPPDATA%\HELM\connector-connector-mcp\logs\scheduled-reauth.log`. The same renewal is available through the `cc_reauth` MCP tool (registry ids only) and may be called by any scheduler (for example a Claude Routine staging a helm-workflow-runner job that runs the command in step 3; the ready-made prompt is `docs/weekly-reauth-routine.md`).
5. **[SCRIPTED]** A second renewer on another host (for a Google account whose token must not depend on one machine). Deploy cc there (`node scripts\deploy.mjs production <tag>`), then register its own task: `.\scripts\install-reauth-task.ps1 -TaskName 'cc-mcp Google Reauth (second)' -DaysInterval 1 -At 15:30 -Connectors <id> -OnlyIfOlderThanDays 4.75 -SkipCoverage -Start`. It checks the renewal record cc writes next to `token.json` (`token.renewed.json`: when, by which host) over the same ssh channel before touching the vault or a browser, logs `skipped - renewed N day(s) ago by <host>` when the first job renewed recently, and renews only when the record is older, missing, unreadable or dated in the future. The same flag works by hand: `node bin\cc.mjs reauth <id> --only-if-older-than 4.75 [--dry-run]`, and through the MCP tool as `cc_reauth` with `only_if_older_than_days: 4.75`. **Gate transport** (`host.transport: "gate"`, `host.credentialsFile`): for a login whose ssh key is bound to a forced command that allows only `put <container> <file>` (content on stdin, up to 64 KiB, atomic) and `health <container>` (the `/health` body, then a last line `HTTP <code>`); anything else is refused (exit 3). cc then uses only ssh: `put` delivers `token.json` and `token.renewed.json`, `health` feeds the same `contains` / `expectRenewedAt` check, and a failed check puts the previous files back with `put` again. The gate offers no read, so `credentials.json` is read from `host.credentialsFile` on the renewer machine, and the files cc delivered are mirrored in `CC_GATE_MIRROR` (default `~/.cc/gate-mirror/<container>`, mode 0600) for the restore of the previous token only; `--only-if-older-than` reads the last renewal time from the `renewedAt` the server's health body echoes, so both renewers see each other's renewals (no answer or no `renewedAt` means renew). `secretsDir` must end in the container folder name; `restart` is not allowed; `health.url` is not sent (the gate knows the port). "Permission denied" from the login is an error that says to tell the operator, never a retry (right after a NAS restart the key can fail for about two minutes). Default transport is unchanged (scp + ssh). A target that is a Google account and not an MCP connector uses a registry entry with `googleOAuth`, `platforms: []`, `auth: {"mode": "none"}` and no `url`. **Renewer hosts:** `googleOAuth.renewers: ["KNOTTYAI-PC"]` (machine names, case-insensitive, compared with `os.hostname()` or a `CC_HOST_NAME` override) limits who renews the entry in a bulk run: on any other machine `cc reauth --all` (also `--all --dry-run` and `cc_reauth` with `["*"]`) prints `skipped - not a renewer on <host>` for it and does not count that as a failure, while naming the id (`cc reauth helm-handoff-robot`, or `-Connectors` in the scheduled task) always runs it. The coverage guard (`cc audit --google`) is unaffected.

6. **[SCRIPTED]** A server that re-reads `token.json` itself needs no `restart`: give the registry entry a `health` block only (`url`, `contains`, `waitSeconds`). Add `"expectRenewedAt": true` and cc requires the health page to show the `renewedAt` it just wrote to `token.renewed.json` next to `token.json` (the server must echo it), so a page that is still ok on the old token cannot pass. On failure the previous token and record are put back.
7. **[MANUAL]** Only if the log says Google asked for 2-step verification (or a screen cc does not know): approve the prompt on the phone within 90 s, or run the connector's own consent flow by hand (its README: `npm run auth:url`, open the printed link in a browser signed in to the Google account, click through, copy the failed `http://localhost/?code=...` address, `npm run auth:exchange -- '<address>'`, restart the connector). If Google changed a screen, fix `data/selectors/google-consent.json` (or the step in `src/browser/googleConsent.ts`) and re-run step 3.

## Thread list (`cc threads`)
Read-only look at the claude.ai/code thread list: `node bin\cc.mjs threads [--json]`. One cc browser (own lane, admission gate, cloned master profile) opens https://claude.ai/code, reads every row as id, status and title (status words as the page shows them: Running, Unread response, Awaiting input, or `none`), and prints plainly what it could and could not read: count and whether the list is complete (the sidebar pages in blocks behind a "Show N more in Recents" button; cc clicks only that button), whether the Cloudflare clearance cookie (`cf_clearance`, name only, never the value) is in the saved master profile, time taken, browsers/Chrome processes used, and any human-check page or sign-in loss (reported, never worked around; exit 1). It never types, submits, renames or archives, and no scheduled task exists for it. Page facts: `data/selectors/claude-code.json`. Since v0.2.8 it never waits for a `cc reauth` renewal and never refuses to run beside another `cc threads` (any number of reads and renewals may run at once; each uses its own copy of the master profile, the lane slots and admission gate police capacity, and the one shared write is a short locked merge of changed cookies); the old advice to keep it out of the reauth task's window no longer applies.
