# connector-connector-mcp ("cc") — rules for any session working here

cc is the SINGLE source of truth for adding, removing, updating, listing and verifying MCP connectors on claude.ai, ChatGPT and Grok.
Connector repos must NOT carry their own registration scripts. If you are asked to register a connector, use cc; do not write a script.

## Hard rules
1. **Nothing connector-specific in `src/`.** Connector facts (id, name, URLs, secret references, enabled platforms) live ONLY in `registry/connectors.json`.
   `test/core.test.ts` ("universality") fails the build if a seeded connector's id/name/host/env var appears in `src/`. Never weaken that test; fix the code.
2. **Secrets: references only.** The registry stores `envFile | env | fileRegex | vault | template` sources, never values. Never print, log, return or screenshot a secret
   or a tokenized URL. All output goes through `Redactor`. MCP tools take registry ids only (the server rejects unknown arguments).
3. **Platform UI facts live in `data/selectors/<platform>.json`**, not buried in code. When a UI drifts, fix the data file or the adapter step, then re-run the platform's exit test.
4. **A result is only real if read back.** `add` is not done until `verify` sees it; `remove` is not done until a fresh list no longer shows it. Adapters must never report success on a hunch;
   prefer `error` over a false `ok`. Poll for asynchronous registration instead of reading once.
5. **Browser rules (learned the hard way):** every run drives its OWN Chrome process (one process per connector sequence), attached over CDP to a normally launched
   chrome.exe (NEVER `launchPersistentContext`: claude.ai's anti-automation sends a Playwright-launched persistent context into a challenge/logout loop). Never dump full page text
   (the grok/chatgpt sidebars contain private chat titles); scope snapshots to a dialog.
   **Browser model (src/browser):** every run drives its OWN Chrome process(es), and a call that covers several platforms gives each platform its own worker and its own browser (`CC_PLATFORM_PARALLELISM` caps how many run together, default all).
   Connectors on one platform always stay sequential, because two adds in one account can race on that platform's list. A browser claims a lane (`lanes.ts`: numbered slot, CDP port = base+index, cross-process lock file, bounded by `CC_MAX_CONCURRENCY`, default 4;
   a full house waits, then errors clearly), clones the sign-in state of the COLD master profile (`CC_BROWSER_MASTER`, default `<helm base>/browser-master`) into a private temp dir (`profile.ts`), launches Chrome on that copy, and on `close()` shuts that Chrome down,
   deletes the copy and frees the lane. Refreshed sessions are merged back cookie by cookie: only the sign-in cookies a healthy browser (every platform it touched still has its sign-in cookie) ROTATED during the run, by a short-lived Chrome that holds the master lock (`mergeCookiesIntoMaster`).
   **The host is shared (other threads' browsers, transcription jobs) and is currently a weak laptop: cc must be a polite neighbour.** (1) *Admission gate* (`lanes.ts` + `hostload.ts`): a browser that is not the only one running is admitted only when (a) the hardware can carry one more (cores x `CC_ADMIT_MAX_CPU` (default 60%) / ~1.7 cores per cc Chrome: 2 on this 8-core laptop, 11 on a 32-core server),
   (b) the newest browser has settled (`CC_ADMIT_SETTLE_MS`, 8 s: a browser's load only shows after it has loaded its pages, so judging earlier admits a herd, as measured), and (c) measured host CPU is under the limit and free memory over `CC_ADMIT_MIN_FREE_GB` (1.5). Decisions are made one browser at a time (an admission mutex),
   waiting browsers do not count as running, the first browser is never held back, and a gate closed for `CC_ADMIT_WAIT_MS` (120 s) lets the browser through anyway. So parallelism is automatic: weak or busy host, platforms run about one after another; strong idle host, they overlap, no configuration. (2) cc's Chrome runs at BELOW-NORMAL priority (`CC_CHROME_PRIORITY=normal` opts out) with lean flags (no background networking, sync, component updates, pings or telemetry), and a warm per-lane HTTP cache (`CC_CACHE_DIR`, `CC_CACHE_MB`, ~25% less CPU on ChatGPT).
   (3) Nothing in cc may busy-wait: waits are sleeps or polls of 500 ms or slower (`polling: 500` on `waitForFunction`; the default polls every animation frame). Why it matters: measured on the HELM host, a cc Chrome burns ~1.7 of 8 cores, and three at once WITHOUT the gate ran slower than one after another (68-81 s vs 114-213 s).
   **Invariants that protect it:** (a) a browser belongs to exactly one run and one platform: never attach to a port you do not hold the lane for, never close or reuse another run's tabs; (b) never open the master with a browser while runs may clone it
   (only `cc browser seed` and the merge do, both under the master lock, and clones refuse a master a foreign Chrome has open); (c) unchanged cookies are never written back, so an older copy cannot overwrite a newer master; (d) nothing in `src/browser` may leave a Chrome, a temp profile or a lane lock behind, on success or on failure;
   (e) lock order is always lane first, then master lock (a merge or seed claims its own lane before taking the master lock, and a run frees its lane before merging), so they cannot deadlock; (f) the old shared Chrome (the HELM browser on 9222, `CC_CHROME_PROFILE`) is not used by cc any more;
   (g) new waiting code must sleep, never spin, and new browser launches must go through `launchChrome` (priority, lean flags, cache) and `acquireLane` (admission).
   Tests: `test/browser-concurrency.test.ts` and `test/politeness.test.ts` run real Chromium; `test/parallel-platforms.test.ts` covers the runner.
6. **Logins** come from the vault inside this process (`bw serve`), never via a vault MCP tool call. ChatGPT's SMS code goes through a one-time vault entry (`ChatGPT SMS code`).
7. **Throwaway test connector:** `registry/selftest.json` (`cc-selftest`). Exit test per platform = add → verify → remove → verify, twice, then confirm real connectors are untouched.
8. **Google OAuth renewal lives here, not in connector repos** (operator, 2026-10-03). A connector that holds a Google refresh token (`credentials.json` + `token.json`) gets a `googleOAuth` block in its registry entry and is renewed by `cc reauth` (CLI) / `cc_reauth` (MCP), scheduled by `scripts/run-reauth.ps1` + `scripts/install-reauth-task.ps1`. Connector repos must NOT carry reauth / renew-token scripts or browser automation for Google's consent screen (`cc audit --scan` flags them); the connector's own `auth:url` / `auth:exchange` flow stays as the manual fallback. The Google consent screen is driven by `src/browser/googleConsent.ts` with its facts in `data/selectors/google-consent.json`.
   **Coverage guard:** a registry entry with a `googleOAuth` block MUST carry `repo` ("owner/name"); `cc audit --google [--root <dir>] [--github <owner>]` (also run at the end of every `scripts/run-reauth.ps1`) fails when a repo uses Google OAuth (a Google client library in a manifest, or token.json + credentials.json + a refresh token in source) and no entry covers it. A repo that legitimately has no grant, or is not deployed yet, goes in `googleOAuthExemptions` with a reason and kind `exempt` or `pending`; never silence the guard any other way.
   **This and the claude.ai sign-in below are the ONLY exceptions to "cc never clicks a consent/Approve button"** (that rule still governs `auth.oauthLogin`), and it is bounded: only for a registry-declared `googleOAuth` target; only while the page is on Google's own hosts (any other host stops it); only for a consent URL cc built itself from the declared scopes; it stops the moment the loopback redirect delivers the result; the granted scopes must include every declared scope or nothing is written; it fills only the Google account's own email/password from the vault. Never widen it to another origin, another account, or any button outside that flow. Everything else is the usual rules: browser via `openSession` (lane + admission gate, one browser per call), output through `Redactor` (never a code, token, client secret or password; logged URLs are origin + path only), no new dependency, nothing connector-specific in `src/`. Proof: `test/reauth.test.ts` (orchestration, rollback, redaction, lock) and `test/google-consent.test.ts` (real Chromium against a fake Google).
   **Second, narrower exception: `cc browser signin` (operator, 2026-10-19).** It signs an account listed in `registry/accounts.json` in to claude.ai with Google, inside that account's own master profile. On claude.ai it clicks only "Continue with Google"; on Google's own hosts only that account's email, password, authenticator code (when `totp`), the account-chooser tile holding THAT email, and "Continue" (`advanceOneStep` "signin" mode); never a checkbox, Allow, Advanced or "Go to (unsafe)"; it refuses a vault entry for another email and removes a sign-in claude.ai reports for another email. Proof: `test/signin.test.ts`.
9. **claude.ai account settings: `cc settings apply|verify --account <id> [--dry-run]` (operator's instruction of 3 Nov 2026).** The operator's words: "anything that you may not be able to necessarily do programmatically here you do have the ability to use [the browser tools in the claude.ai UI] to apply or solve those gaps". cc may therefore click in the claude.ai UI for this ONE purpose, bounded as follows, and for nothing else:
   only on claude.ai's own origin (the hosts in `data/selectors/claude-settings.json`; any other host stops the run); only inside a clone of the signed-in account's own master profile (`openSession({ master })`, lane + admission gate, one browser per call); only for an account whose `registry/accounts.json` entry declares `settings.projects`.
   The only controls it may click: create-project (and the create form's submit), the project's instructions editor (opening it) and its Save/confirm button. Opening the Projects list, a project and its settings page is read-only and is done by navigation, not clicks; a read closes the editor with a key press.
   Never a sign-in control, never Delete/Remove/Rename/Archive/Share/Invite/Upgrade/billing, never connector toggles, memory or preferences, never another project, chat or sharing setting. This bound is enforced in code (`guardedClick` and `CLICK_DENY` in `src/adapters/claudeSettings.ts`), not in the data file, so no selector edit can widen it.
   Behaviour: `apply` opens the project with exactly the declared name, or creates it when none exists (a near-identical name or two exact matches is refused, never renamed or guessed); it writes the instructions only when their sha256 differs, then reopens the project and reads them back before it reports ok. `verify` only reads and compares. `--dry-run` opens no browser. A human check or a sign-in page stops the run and is reported, never worked around.
   The instruction text is a reference (`instructions: { "type": "file", "path" }`), never stored in the registry or repo, and never printed, logged or returned: output is only "N characters, sha256 <prefix>", through `Redactor`. Log: `logs/settings/<account>.log`. Proof: `test/settings.test.ts` (refusals, idempotence, read-back, redaction, deny list) and `test/settings-browser.test.ts` (real Chromium against a fake claude.ai).

## Test connectors are on-demand (operator policy)
Connectors with `"tier": "test"` (helm-audio-mcp-test, helm-drive-mcp-test, patchright-mcp-test, connector-connector-test) must NOT stay registered on the platforms
unless someone is actively developing or testing them. `--all` / `"*"` skips them unless `--include-test` (CLI) / `include_test` (MCP). The operator or any thread may ask
cc to bring one up (`cc add helm-audio-mcp-test --platform all`) or take it down (`cc remove helm-audio-mcp-test --platform all`) at will; naming it explicitly always works.
After a test session ends, remove it again and run `cc list --platform all` to confirm.

Promotion rule (operator, 2026-10-02): test is for development and functionality verification, never a standing parallel deployment. The moment a connector's production tier is deployed and verified working (see the per-platform verified-state definitions below) on every platform it's registered on, its matching test-tier connector comes down as part of that same promotion - this is not optional and not something to wait to be asked about a second time once the operator has set this expectation. Confirmed-live case: fleet-connect-test stayed up through fleet-connect's full deploy-and-verify cycle (needed to prove the server before cutover), then was removed from all 3 platforms the moment fleet-connect (production) verified ok everywhere.

## What "verified" means per platform
- **Claude:** the connector row exists and shows Connected.
- **Grok:** the connector is in the Connected list.
- **ChatGPT:** the connector is in the Installed list AND its own page shows Connected. Installing alone is not enough: ChatGPT also needs its Connect step (button, then confirmation dialog), which `cc add` performs and `cc add --if-existing skip` repairs.
  ChatGPT lists no discovered tools anywhere on the page (probed 2026-10-02), so cc cannot prove a tool scan; it only proves the connection state ChatGPT displays.
- `--platform` takes one or more platforms, or `all`: `--platform chatgpt grok`.

## Accounts (operator, 2026-10-19)
cc works in several claude.ai accounts side by side: `registry/accounts.json` (data only), one cold master profile per account, `--account <id>` on every op (MCP `account`), `cc browser signin --account <id>` / `cc_signin` to sign one in from its vault entry. Never run one account's work in another account's master; never put an account's email, vault label or folder in `src/`. Design: `docs/SPEC.md` section 11.

## Layout
`bin/cc.mjs` CLI · `src/core` registry/secrets/redaction/runner/reauth/transport · `src/adapters/{claude,chatgpt,grok}.ts` · `src/browser` (incl. `googleConsent.ts`) · `src/server` MCP front door ·
`data/selectors` · `registry` · `scripts` deploy/start/tunnel/tasks · `tools/probe` read-only diagnostics · `docs/SPEC.md`.

## Commands
`npm test` · `npm run build` · `node bin/cc.mjs <add|remove|update|verify|list|probe> [ids|--all] --platform <claude|chatgpt|grok ...>|all [--account <id>] [--dry-run] [--registry <path>]` ·
`node bin/cc.mjs reauth <ids|--all> [--include-test] [--dry-run]` (Google OAuth renewal) · `node bin/cc.mjs browser seed|check|signin [--account <id>]` (master profiles) · `node bin/cc.mjs settings apply|verify --account <id> [--dry-run]` (claude.ai Project instructions, rule 9) · `node bin/cc.mjs accounts` · `node bin/cc.mjs audit --scan <repo-root>` (finds registration-script look-alikes in other repos).
Host: `CC_BROWSER_MASTER` (cold master profile), `CC_MAX_CONCURRENCY`, `CC_PLATFORM_PARALLELISM`, `CC_ADMIT_MAX_CPU`, `CC_TRACE=1` (per-step timings and admission waits on stderr), `CC_CHROME_PATH`, `CC_DEBUG=1` (redacted step dumps), deploy with `scripts/setup-host.ps1`, `scripts/deploy.mjs`, `scripts/install-tasks.ps1`.

## Engineering standards (standing direction from the operator)

This project follows the operator's standing direction in `trentet/helm-engineering-standards` (`docs/standards.md`): isolated dev/test/production, immutable versioned artifacts in a central registry as the
source of truth, build once and promote, pinned dependencies, library-first layering. Most of it is a future target, but keep it in mind in every decision.
**Anything that could conflict with it must be raised with the operator before it is decided - never resolved automatically** (examples: deploying a branch instead of a tagged artifact to production, building on
the machine it runs on and calling that the release, test/production reading files from a dev environment, installing from outside the agreed registry/lockfile, unpinned dependencies, sharing credentials or data between environments).
