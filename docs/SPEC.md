# SPEC -- connector-connector-mcp v0.3 (APPROVED 2026-10-01; status updated 2026-10-02)

Status: plan approved by operator 2026-10-01. Language: TypeScript. Server hostname: cc.trentt.me.
Owner decision (operator, 2026-10-01): ONE universal tool registers ANY connector on ANY platform
(claude.ai, ChatGPT, Grok). Connector repos hold NO registration scripts.

## 1. Architecture

    connector-connector-mcp/
      bin/cc                      single entry point (CLI)  ->  `cc <op> <connector|--all> --platform <p|all>`
      src/
        core/                     registry loader, secret resolver, redaction, orchestrator, result model
        browser/                  Patchright over CDP (the ONLY place a browser is touched)
        adapters/{claude,chatgpt,grok}/   one adapter per platform, same interface
        server/                   MCP server front door (Streamable HTTP, token-gated)
      data/
        selectors/{claude,chatgpt,grok}.json   flow + selector maps (data, not code; drift is fixed here)
      registry/connectors.json    connector definitions: NO secret values, only references
      test/  deploy/  docs/

Rules that make it universal:
- The runner knows operations and platforms, never a specific connector. Connector facts live only in
  `registry/connectors.json`. A test fails the build if any seeded connector's id, name, host or env var
  appears in `src/`.
- Adapters implement one interface: `probe, list, add, remove, update, verify` (+ `dryRun`). The runner
  dispatches `op x connector x platform`; adding a platform = adding an adapter + a selector file.
- Both front doors (CLI, MCP server) call the same `core.run(request)`; no logic lives in either.
- Idempotent: `add` on an existing connector is a no-op unless `--if-existing update|fail`.

## 2. Connector definition (registry)
`id, name, description, url (literal | template), auth {mode: header|tokenUrl|oauth|none, headerName?},
secrets {name: ref}, platforms[]`. Secret refs: `envFile(path,key) | env(var) | vault(label) |
fileRegex | literal(non-secret only)`. Reuses the source-type design of the existing ChatGPT registrar.
Secrets are resolved in-process at run time; never stored, logged, echoed, or returned (tokenized URLs
redacted in all output). MCP callers pass a registry id, not a token.

## 3. Operations
`add, remove, update, list, verify, dry-run, probe`. `verify` = confirm on the live platform that the
connector is registered AND connected (tools discovered), not merely that the add form submitted.
Failure => screenshot to `artifacts/` (redacted), non-zero exit, structured error.

### Findings that changed the design
- ChatGPT and Grok are header-less: header-auth connectors need urlByPlatform (a tokenized URL), and the SERVER must accept ?token=.
  Servers must accept a ?token= for these platforms. Which value that token carries is each connector's own auth design, not something cc mandates: Vault MCP uses a separate, low-privilege query token distinct from its header token; Fleet Connect (operator decision, 2026-10-02) instead accepts one single token identically via header and query, for now - a tiered model may return later as that project matures. A connector that cannot accept ?token= at all stays Claude-only.
- claude.ai refuses a second connector with an existing URL ("already exists in your organization").
- Platforms show different display names for the same connector (nameByPlatform): claude "HELM Drive Connector", chatgpt "HELM Drive MCP Connector", grok "HELMMCP".
- Rows in claude.ai's list contain icon-font characters; Grok registers asynchronously (poll); ChatGPT's Authentication is a native <select>, Remove is Delete plugin on the plugin page;
  Grok's Custom tile is a button inside the dialog.
- ChatGPT login needs an SMS code unless the Chrome session persists; the code is supplied through a one-time vault entry, never typed into a chat.

## 9. Browser concurrency model (2026-10-02)
Problem: one shared Chrome (fixed CDP port, one profile, `contexts()[0]`) meant concurrent callers stomped each other's pages ("Target page, context or browser has been closed").
Design chosen: **ephemeral per-run profile copy of a cold master, plus a lane slot allocator**. Rejected: a fixed pool of N independently logged-in lanes (N manual logins, including a Claude Google login cc cannot automate, and a ChatGPT SMS code per lane).
- **Run = one Chrome.** `openSession()` claims a lane (`src/browser/lanes.ts`): slot i, CDP port `CC_LANE_PORT_BASE`(9400)+i, exclusive lock file in `CC_LANES_DIR` (default `<tmp>/cc-lanes`), stale locks (dead pid or >45 min) reclaimed, a port that a foreign process holds skips the slot, full house waits `CC_LANE_WAIT_MS` then errors clearly. Max `CC_MAX_CONCURRENCY` (default 4, about what 8 cores carry at ~1.7 cores per cc Chrome) across ALL processes (CLI, server).
- **Clone, launch, attach.** `src/browser/profile.ts` copies the master's sign-in state only (Local State, Preferences, cookies in both `Default/Network/Cookies` and `Default/Cookies`, Local/Session Storage, IndexedDB, Web Data) into a temp dir, then `chrome.ts` starts a normally launched Chrome on a free lane port and attaches with `connectOverCDP`. Never `launchPersistentContext`.
- **The master is cold.** `CC_BROWSER_MASTER` (default `<helm base>/browser-master`). A Chrome running on it makes copies unreliable, so clone and write-back refuse it. It is seeded once from an already signed-in Chrome by `cc browser seed --from-port 9222` (cookies read over CDP in memory, re-written by a normal Chrome on the master; platform facts, which cookie proves sign-in and which hosts hold session state, live in `data/selectors/<platform>.json` under `auth`). `cc browser check` proves it.
- **Staleness answer (cookie-level merge).** At open, the run records its platform sign-in cookies (`auth.refresh` in the selectors file). At close, if every platform the browser touched still has its sign-in cookie, the cookies whose value CHANGED during the run (rotated or newly issued; session-only ones are made persistent) are merged into the master by a short-lived Chrome that holds a lane and then the master lock; clones wait on that lock. Unchanged cookies are never written, so a browser that started from an older master cannot overwrite a newer value; a signed-out browser never writes. This replaced an earlier whole-file write-back with a generation counter, which would have dropped two of three platforms' rotations when sibling browsers finish together.
- **Platforms in parallel, politely.** A call covering several platforms gives each platform its own worker with its own lazily opened browser (a platform with nothing to do never opens one); items within one platform stay sequential; results keep connector-major, platform-minor order; a failed open is remembered per platform. `CC_PLATFORM_PARALLELISM` caps how many workers run together (default all).
  **Admission gate (`lanes.ts`, `hostload.ts`).** The host is shared and, today, weak (8 logical cores of a ~12-year-old laptop, other workloads running). A browser that is not the only one running is admitted only when (a) hardware capacity allows one more (cores x `CC_ADMIT_MAX_CPU` (60%) / ~1.7 cores per cc Chrome, `CC_BROWSER_CORES`: 2 here, 11 on 32 cores), (b) the newest browser has settled (`CC_ADMIT_SETTLE_MS`, 8 s), and (c) measured CPU is below the limit and free memory above `CC_ADMIT_MIN_FREE_GB` (1.5). The first browser is never held back; after `CC_ADMIT_WAIT_MS` (120 s) it goes ahead anyway (slow beats failed). Decisions are serialized by an admission mutex and lanes still waiting at the gate do not count as running (without both, two waiters deadlock or both go). CPU is sampled from `os.cpus()` (no WMI, no child processes) and a waiter sleeps. The settle rule exists because the first live test of an unsettled gate admitted all three browsers within 4 s and burned 349 Chrome CPU-seconds against 138 sequential. The same code runs platforms about one after another on this laptop and overlaps them on a strong idle machine, with no per-host tuning, which matters because the workloads move to more powerful machines later.
  **Why a gate and not a fixed default.** Measured with `CC_TRACE=1`, `verify helm-drive --platform all`: one after another 181 s / 81 s / 68 s, all three at once with no gate 213 s / 114 s / (chatgpt alone 122 s). A single cc Chrome used ~47-51 CPU-seconds over a 29 s verify (~1.7 cores); `--disable-gpu` changed nothing. Ungated overlap saturated the CPU and slowed every browser superlinearly.
  **Result after the fixes (HELM host, `CC_TRACE=1`, `verify helm-drive --platform all`):** default (gate on, overlap allowed) 40 s wall, 53 Chrome CPU-seconds, at most 2 browsers; forced one-at-a-time 50 s, 31 CPU-seconds, 1 browser; a single-platform verify 12 s, 25 CPU-seconds (was 20 s, 39). Before the gate: overlap 118-213 s and 349 CPU-seconds. Two bugs found on the way, both by measuring: the gate judged load before a new browser's load appeared (herd), and a platform's browser stayed open until the whole call ended (so "one at a time" held three lanes and the third platform waited out the 120 s limit).
  **Footprint reductions.** cc's Chrome runs at below-normal priority (`os.setPriority`, Chrome's children inherit it on Windows; `CC_CHROME_PRIORITY=normal` opts out); lean launch flags (no background networking, sync, component updates, pings, telemetry; deliberately not the automation flag set); a persistent HTTP cache per lane (`<helm base>/browser-cache/lane-<i>`, 100-150 MB cap, exclusive through the lane lock): measured warm vs cold, ChatGPT 45 to 34 Chrome CPU-seconds and 30 s to 23 s, Claude 41 to 36; adapters poll the DOM every 500 ms instead of every animation frame.
- **Lifecycle.** `close()` shuts Chrome down over CDP, waits for the process, force-kills the tree after 15 s, deletes the temp profile, frees the lane. A failure during open cleans up the same way. The runner remembers a failed open so the remaining items fail fast with the same error.
- **Server.** The old run queue (`serialize()`) is gone: `cc_run` calls run in parallel, each in its own browser, bounded by the lanes.
- **Proof.** `test/browser-concurrency.test.ts` (real Chromium): distinct ports/processes/profiles for simultaneous runs; state set in one invisible to another and one run closing does not disturb the other; lane waiting and clear error; cookie-level merge (rotated only, older copy never overwrites, signed-out writes nothing, sibling platforms both merge); refusal of a hot master; one run over three platforms driving three simultaneous browsers when parallelism is requested; and two simultaneous `run()` calls (add and verify of `registry/selftest.json`'s connector) that complete without crossing. `test/parallel-platforms.test.ts` covers the runner (overlap, per-platform sessions, ordering, cap, failure isolation). Live acceptance on the host is recorded in the Drive session notes.

## 10. Google OAuth renewal: `cc reauth` (2026-10-03, issue #33)
Problem: a connector that talks to Google holds a refresh token (`token.json`) that Google expires after 7 days while the OAuth app stays in Testing publishing status (the operator's standing choice, not a gap to close by publishing to Production). Renewing it needs Google's consent screen, i.e. a browser signed in as the operator. That renewal first lived in two connector repos (a helm-drive-mcp-specific script inside patchright-mcp, and a wrapper in helm-audio-mcp). Operator decision: it belongs in cc, the one place that drives a browser on the operator's behalf, and connector repos carry none of it (same rule as registration, section 4a).
- **Data, not code (CLAUDE.md rule 1).** A registry entry may carry `googleOAuth`: `secretsDir` (where `credentials.json` is read and `token.json` written, on the connector's own host), `scopes`, `account.vaultLabel` (the Google account's vault entry), optional `host {ssh, keyFile, port, os, transport, credentialsFile}` (the connector runs on another machine: files move with scp, commands with ssh, key login only; `transport: "gate"` = a forced-command login that allows only `put <container> <file>` and `health <container>`, so cc speaks only those two verbs over ssh (`GateTransport` in `src/core/transport.ts`), refuses any other command itself, reads `credentials.json` from `credentialsFile` locally and mirrors what it delivered in `CC_GATE_MIRROR` for restore-on-failure only; the last renewal time (`--only-if-older-than`, and the record put back after a failed renewal) is the `renewedAt` echoed by the `health` body, so both renewers share it, and no answer or no `renewedAt` reads as "no record" (renew); validated in `registry.ts`: needs `credentialsFile`, no `restart`, `secretsDir` ending in the container folder), optional `restart.command` and `health {url, contains, waitSeconds}` (run and checked on that host). Nothing connector-specific is in `src/`; the universality test still passes.
- **Op.** `cc reauth [ids|--all] [--include-test] [--dry-run]` (CLI) and `cc_reauth` (MCP; registry ids only, strict arguments like `cc_run`). Not platform-bound, so it sits beside `run()`: `src/core/reauth.ts` (orchestration, both front doors), `src/core/transport.ts` (this machine or ssh/scp), `src/browser/googleConsent.ts` + `data/selectors/google-consent.json` (Google's screens, as data).
- **Per connector, in order:** read `credentials.json` (a Desktop-app client with a localhost redirect) -> start a loopback HTTP server on an ephemeral port that accepts only the `state` cc generated -> build the consent URL from the DECLARED scopes (`access_type=offline`, `prompt=consent`, `login_hint` = the vault account) -> drive Google's screens in cc's own browser session (cloned master profile, own lane, admission gate: CLAUDE.md rule 5; ONE browser for the whole call) until the loopback has the code -> exchange it at Google's token endpoint with a single `fetch` (no new dependency) -> require a refresh token AND every declared scope, else write nothing -> deliver `token.json` (written beside, then moved over; over ssh when remote) -> run `restart.command` -> poll `health` -> if the restart or health check fails, put the previous token back and restart again. The temporary stage for a remote file is always deleted. A failure at any step before delivery changes nothing.
- **Consent exception (bounded).** cc has never clicked a consent/Approve button (`oauthLogin`, section 8 and ADOPTION.md). `cc reauth` is a single, explicit exception: only for a registry-declared `googleOAuth` target; only while the page is on Google's own hosts (any other host stops it); only for a URL cc built itself from the declared scopes; it stops touching the page the moment the redirect delivered the result; the granted scopes are verified afterwards. It fills nothing but the Google account's own email/password from the vault (resolved in-process, never logged). A 2-step-verification challenge it cannot pass is waited on for 90 s and then reported, never guessed at; the manual fallback is the connector's own consent flow.
- **Safety properties** (all tested): the loopback rejects a wrong `state`; fewer scopes than declared or no refresh token writes nothing; a failed health check restores the previous token; a per-connector lock file stops two renewals (CLI, scheduled task, MCP) running at once; the dry run opens no browser and writes nothing; no code, token, client secret or password appears in any output (everything goes through `Redactor`) and every logged URL is origin + path only. Log: `<helm data base>/logs/reauth.log`.
- **Scheduling.** `scripts/run-reauth.ps1` (runs `cc reauth --all` from the deployed copy, logs to `logs/scheduled-reauth.log`) and `scripts/install-reauth-task.ps1` (Scheduled Task "cc-mcp Google Reauth", every 5 days, inside Google's 7-day limit; also switches on Task Scheduler history and retires the legacy "HELM helm-drive-mcp Google Reauth" task). A Claude Routine that stages a helm-workflow-runner job may call the same command; both are just schedulers.
- **Second renewer (2026-10-05, #39, design in #37).** `token.renewed.json` (`renewedAt`, `byHost`) is written next to `token.json` through the same atomic replace, only after a fully successful renewal (delivered, restarted and healthy, or delivered with no restart configured); a failed or restored renewal writes nothing, and a write failure only logs (the other job then renews again, the safe direction). `cc reauth --only-if-older-than <days>` reads it first, before credentials, vault or browser, and reports `skipped` when it is newer; missing, unreadable, undated or future-dated (more than 5 minutes ahead) means renew. `token.json`'s `expiry_date` and file time are never used: a server that saves refreshed access tokens would make an old grant look fresh forever. A registry entry with `googleOAuth` may have `platforms: []` and no `url` (a Google account, not an MCP connector); platform ops skip it. Locks are per machine, so two hosts are kept apart by schedule (a second job at a different time of day), not by a lock; a double renewal is harmless because the previous token stays valid until it expires.
- **Input checks and extras (2026-10-11, #44, leftovers of closed #41).** `install-reauth-task.ps1` / `run-reauth.ps1` reject bad input before anything runs: `-DaysInterval` 1 to 6, `-OnlyIfOlderThanDays` 0 to 6, `-TaskName` letters/digits/space/`()._-`, `-Connectors` kebab-case ids only (they reach a command line). A `googleOAuth` entry with no `platforms` is normalised to `[]`; a non-Google-only entry without `url` says "url: required". `--dry-run --only-if-older-than` says `would renew: ...` when the record is old or missing (`would skip` otherwise); a failed `token.renewed.json` write is a `WARNING` in the item detail as well as the log.
- **MCP parity (2026-10-11).** `cc_reauth` takes the same options as the CLI: `connectors` (ids or `["*"]`), `include_test`, `dry_run` and `only_if_older_than_days` (a positive number, validated by the tool schema like the CLI's `--only-if-older-than`; zero, negative or non-numeric is an error and nothing runs). It maps to `onlyIfOlderThanDays` on the same `reauth()` call. The coverage skip (`-SkipCoverage`) is a flag of `scripts/run-reauth.ps1`, not of `cc reauth`, so it has no MCP counterpart. A deployed server only offers the option after it is redeployed.
- **Health without a restart (2026-10-09, #43).** A `health` block no longer needs `restart`: for a server that re-reads `token.json` itself, cc delivers the token, polls the health URL (on the connector's host) for up to `waitSeconds`, and restores the previous token if the page never matches. A page that already says ok on the OLD token would pass at once, so `health.expectRenewedAt: true` makes cc write `token.renewed.json` FIRST and require the health body to contain that record's `renewedAt` (the server echoes the value it read from the record next to its token file). On failure the previous token and the previous record are put back (an undated record if there was none, which reads as "renew" for `--only-if-older-than`); the check after a restore asks only for plain health. `contains` is a plain substring match, so the server's JSON must be written compact. Nothing here proves the new token works against Google beyond what the health page reports.
- **Second step (2026-10-16, operator: keep renewing in Testing status, handle Google's second step inside the renewal).** A `googleOAuth.account.totp: true` entry means the account's vault item also holds its authenticator (TOTP) secret. When Google shows its authenticator page (`/signin/challenge/totp`), `googleConsent.ts` fetches the current code from `bw serve` (`GET /object/totp/:id`, no premium plan needed on our Vaultwarden, tested 2026-10-16) at that moment, in-process, and types it; the code is never logged or returned, and `--dry-run` only says whether the vault can produce one. Without `account.totp` the old behaviour stands (wait for the grace period, then report). The secret and the password sit in one vault: acceptable for robot/service accounts, not for personal accounts. Also: `deleteCredential` now deletes permanently (`?permanent=true`), because `bw serve`'s plain DELETE only moves an item to the trash. Further second-step options: `docs/FUTURE-second-step.md` (branch `claude/future-second-step-options`).
- **Dependencies, each primary with a manual fallback** (operator decision 2026-09-27): vault / `bw serve` (the Google credential), the master browser profile (already signed in to Google through the claude.ai and ChatGPT sign-ins), and for a remote connector the SSH key. If one is down, the connector's own consent flow (its README's `auth:url` / `auth:exchange`) is the manual fallback.
- **Renewer hosts (2026-10-11, #45).** Optional `googleOAuth.renewers: string[]` (validated in `src/core/registry.ts`: non-empty list of host names). `selectGoogleConnectors` compares them case-insensitively with `hostName()` (`CC_HOST_NAME` or `os.hostname()`) only for the bulk selection (`--all` / `["*"]`): an entry that does not list this machine becomes a `skipped` item `skipped - not a renewer on <host>` (logged, never an `error`, so the run stays ok); naming an id explicitly ignores the list. `helm-handoff-robot` carries `["KNOTTYAI-PC"]` so the W540's weekly `--all` leaves it to the second renewer. The coverage guard looks only at `googleOAuth` + `repo`, so the entry stays covered.
- **Coverage guard (2026-10-04).** `src/googleCoverage.ts` + `cc audit --google [--root <dir> ...] [--github <owner>]`. It reads dependency manifests and a bounded set of source files (local checkouts through `.git/config`, or every non-archived repo of a GitHub owner through `gh api`, nothing cloned) and prints only repo names, paths and the NAMES of matched terms. A repo "uses Google" when a Google client library is in a manifest or when token.json, credentials.json and a refresh token all appear in source; generic OAuth words alone are a `review` note. Each such repo must be covered by a registry entry with a `googleOAuth` block and a `repo` field, or listed in `googleOAuthExemptions` (`exempt`: no grant to renew; `pending`: expected once deployed). Exit 1 on `UNCOVERED` or a stale exemption; `scripts/run-reauth.ps1` runs it after every scheduled renewal (exit 3 on a gap). First full audit (32 repos, 2026-10-04): covered helm-drive-mcp and helm-audio-mcp; pending helm-vision-mcp; exempt connector-connector-mcp, dsm-connect, patchright-mcp (leftover); nothing else.
- **Exit test.** Per environment: `cc reauth <id> --dry-run`, then a real run; the connector answers a Drive-backed request afterwards and `token.json` carries a new refresh token. Live runs and results are in the issue.

- **No avoidable waiting (2026-10-17, v0.2.8, operator rule).** Checks and scripts must not wait on each other unless running together would corrupt shared data. `cc threads` therefore takes no lock of its own and no longer waits for `cc reauth` or refuses to run beside another `cc threads` (v0.2.7 did both, for no data reason). What stays: one renewal per connector at a time (two would overwrite the same token file), the master-profile lock around a clone or a cookie merge, and the lane/admission limits that protect the machine (past the browser cap, extra runs queue rather than start). `timing.waitedForReauthMs` stays in the report, always 0. The blocker kinds `reauth-running` and `other-threads-run` are gone.

## 11. Accounts (2026-10-19, v0.2.9, operator: add the second claude.ai account beside the first)
- **Data, not code.** `registry/accounts.json` lists the accounts: `id`, `email`, `platforms`, optional `master` (a folder name next to the default master; exactly one account has none and uses the default master itself), optional `signIn.google { vaultLabel, totp? }`. Loaded and validated by `src/core/accounts.ts`; no account fact is in `src/` (`test/accounts.test.ts` checks emails, non-default ids, folder names and vault labels).
- **Isolation.** An account = its own cold master profile. `run()` resolves the account (`req.account`, else `CC_ACCOUNT`, else `default`; an unknown id fails the whole call and opens nothing), opens every browser on that account's master (`openSession({ master })`), skips platforms the account is not used on, and tags results with `account` when it is not the default. Clones, lanes, admission and cookie merge-back are unchanged, per master. A missing accounts file means one default account on every platform (old behaviour).
- **Sign-in (`cc browser signin`, MCP `cc_signin`).** `src/browser/signin.ts`. Reads the account's vault entry first (optionally waiting for it, before any lock), refuses an entry whose username is not the account's email, then on a lane and under the master lock launches Chrome on the cold master: claude.ai login -> "Continue with Google" -> Google screens in `advanceOneStep(..., "signin")` (email, password, authenticator code when `totp`, the chooser tile holding THAT email only, "Continue"; never a checkbox, Allow, Advanced or "Go to (unsafe)") -> stops when claude.ai's session cookie exists -> reads the signed-in email from `signIn.accountUrl` and, if it is another email, clears claude.ai's cookies from the profile and fails. 2-step verification it cannot pass is waited on for `twoFaGraceMs`, then reported. Facts in `data/selectors/claude.json` `signIn`. This is the second bounded Google exception next to `cc reauth` (CLAUDE.md rule 8), approved by the operator 2026-10-19.
- **Proof.** `test/accounts.test.ts` (file validation, selection, master paths, runner isolation and skips, vault-entry checks), `test/signin.test.ts` (real Chromium against a fake claude.ai and a fake Google on different hosts: happy path, already signed in, an Allow screen stops it, someone else's chooser tile is never clicked, a wrong email is removed), `test/server.test.ts` (`account` on `cc_run`, `cc_signin`, `cc_list_accounts`, smuggled fields refused).

## 12. Account settings: `cc settings` (2026-11-03, issue #74, operator: solve what cannot be done programmatically through the claude.ai UI)
- **Why.** A new claude.ai account needs a Project whose instructions hold HELM's loader stub; claude.ai offers no supported API for that, so cc drives the UI, bounded by CLAUDE.md rule 9.
- **Data.** `registry/accounts.json` `settings.projects[] { name, instructions: { type: "file", path } }` (validated in `src/core/accounts.ts`; `%VAR%` expanded, absolute path required). The text stays in its file. Page facts: `data/selectors/claude-settings.json`, every entry `{ value, status }` with `status` "unverified" until seen live; cc prints the unverified count on every run.
- **Code.** `src/core/settings.ts` (pre-checks, exact-name plan, idempotence, read-back, redacted output and log) and `src/adapters/claudeSettings.ts` (page driver; the only clicks go through `guardedClick`: claude.ai hosts, four roles, `CLICK_DENY`). - **Flow (apply).** Resolve the account and every file (any failure: stop, no browser) -> one browser on the account's master clone -> read the Projects list until its count is stable -> exact match opens, none creates (then re-list and require exactly one), near match or duplicates refuse -> open the editor, compare sha256 and length with the file -> write only on a difference -> reopen the project and read back (up to `readBackAttempts`, `readBackDelayMs` apart) -> "ok ... N characters, sha256 <12 hex>". `verify` is the same read without any write; `--dry-run` stops before the browser.
